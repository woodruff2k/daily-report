# 편집한 파일 검사

## 1. 대상 파일을 정한다

인자로 경로가 주어졌으면 그것을 쓴다. 없으면 git 에서 뽑는다.

```bash
git status --porcelain -uall | awk '{print $NF}'
```

**`-uall` 을 빠뜨리지 마라.** 없으면 미추적 항목이 **디렉터리로 뭉쳐** 나온다(`src/app/(probe)/`). 그 경로를 prettier·eslint 에 넘기면 의도한 파일을 검사하지 않는다.

스테이지·미스테이지·미추적을 모두 포함한다. 이름이 바뀐 파일(`R`)은 `->` 뒤 경로를 쓴다.

검사 대상 확장자는 `.ts` `.tsx` `.css` `.json` `.mjs` `.yml` `.yaml` 다. `lint-staged.config.mjs` 가 쓰는 패턴과 같다.

**대상이 없으면 거기서 멈추고 "검사할 변경이 없다" 고 보고한다.** 아무 명령도 돌리지 않는다.

## 2. 싼 검사부터 돌린다

파일 경로는 **항상 큰따옴표로 감싼다.** 이 저장소에는 `src/app/(auth)/`·`src/app/(main)/` 처럼 **괄호가 든 라우트 그룹 경로**가 있어 인용하지 않으면 셸이 깨뜨린다.

```bash
npx prettier --check "<경로>" ...        # 포맷
npx eslint "<경로>" ...                  # 린트 (.ts/.tsx 만)
npx tsc --noEmit                         # 타입 — 범위를 좁힐 수 없다
npx vitest related --run "<경로>" ...     # 이 변경이 영향을 주는 테스트
```

- **`tsc --noEmit` 은 프로젝트 전체를 본다.** 파일 단위로 좁힐 수 없다. 내가 건드리지 않은 파일에서 오류가 나올 수 있고 **그것도 보고한다** — 내 변경이 다른 곳의 타입을 깨뜨린 경우다.
- `.ts`/`.tsx` 가 하나도 없으면 eslint·tsc·vitest 를 건너뛴다.
- **통합 테스트(`npm run test:integration`)는 돌리지 않는다.** 실제 DB 가 필요하다. 필요하면 사용자가 따로 실행한다.

## 3. 고친다

```bash
npx prettier --write "<경로>" ...
npx eslint --fix "<경로>" ...
```

고친 뒤 다시 검사해 통과를 확인한다. **자동 수정으로 못 고치는 것은 직접 고치거나 보고한다.**

## 4. 하지 않는 것

- **`npm run format` 을 쓰지 않는다.** 저장소 전체를 다시 쓴다(`prettier --write .`). 편집하지 않은 파일까지 바뀌어 diff 가 더러워진다. 파일 단위로 `npx prettier --write` 를 쓴다.
- **`npm run lint` 을 쓰지 않는다.** `src` 전체를 본다. 몇 개 파일만 바꿨으면 그 파일만 본다. (전체 점검이 목적이라면 그때는 써도 된다.)
- **`eslint-disable` 주석을 붙여 경고를 침묵시키지 않는다.** 규칙이 틀렸다고 판단되면 고치지 말고 보고한다.
- **테스트 단언을 약하게 바꾸거나 skip 하지 않는다.** `vitest related` 가 실패하면 그 실패가 내 변경 때문인지 확인해 보고한다.
- **`--no-verify` 로 커밋하지 않는다.** 커밋은 이 스킬의 일이 아니다.
- 커밋·푸시·PR 생성을 하지 않는다.

## 5. 이 저장소의 함정

- **`*.md` 는 `.prettierignore` 대상이다.** prettier 가 건너뛰고 "All matched files use Prettier code style!" 를 출력한다 — 마크다운만 바꿨다면 **검사된 것이 아니라 건너뛰어진 것**이다. 그렇게 보고한다. (한글 표의 칸 폭을 prettier 가 글자 수로 세어 깨뜨리기 때문에 일부러 제외했다.)
- **`package-lock.json` 도 `.prettierignore` 대상이다.** npm 이 소유하는 생성물이다.
- **eslint 종료 코드를 구분한다.** `1` 은 `--fix` 로 못 고친 린트 문제가 남은 것이고 내용은 eslint 가 이미 출력했다. `2` 이상은 eslint 자체가 실행에 실패한 것(설정 오류 등)이다. 둘을 같이 묶어 보고하지 않는다.
- **종료 코드를 파이프 뒤에서 읽지 마라.** `npx eslint "$f" | tail -3` 다음의 `$?` 는 `tail` 의 코드다. 명령을 직접 실행해 받는다.

  ```bash
  npx eslint "$f"; status=$?
  ```
- **`npm test` 는 jsdom 단위 테스트만 돈다.** `*.integration.test.ts` 는 `vitest.config.ts` 의 `exclude` 로 빠져 있다.

## 6. 보고 형식

| 검사 | 결과 |
| :---- | :---- |
| prettier | 통과 / 고침 N개 / 건너뜀(이유) |
| eslint | 통과 / 고침 N개 / 남은 문제 N개 |
| tsc | 통과 / 오류 N개 |
| vitest related | N건 통과 / N건 실패 |

- 검사한 **파일 목록**을 먼저 적는다.
- 고친 것과 남은 것을 나눠 적는다. 남은 것은 `파일경로:줄번호` 와 원인을 적는다.
- **실패를 숨기지 않는다.** 통과하지 못한 검사는 출력과 함께 그대로 보고한다.

## 7. 훅과의 관계

이 저장소는 `.claude/settings.local.json` 에 `PostToolUse` 훅(`format-on-edit.sh`)을 둘 수 있다. 그 훅은 **편집 한 건마다 자동으로** 해당 `.ts`/`.tsx` 에 prettier·eslint 를 돌린다.

이 스킬은 그것과 겹치지 않는 일을 한다.

| | 훅 | 이 스킬 |
| :---- | :---- | :---- |
| 실행 | 편집 직후 자동 | 요청받을 때 |
| 범위 | 그 파일 하나 | 변경 전체 |
| `tsc` | 안 함 (파일 단위로 무의미) | **함** |
| 관련 테스트 | 안 함 | **함** |

**훅이 꺼져 있거나 깨져 있어도 이 스킬은 동작한다.** 둘 중 하나만 있어도 되지만, 훅은 즉시성을, 이 스킬은 묶어서 보는 것을 담당한다.
